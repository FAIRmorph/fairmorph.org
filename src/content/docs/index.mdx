:::caution[Prototype Fund (Germany) · Proof of concept — not production software]
**FAIRmorph is an open-source prototype for Germany's [Prototype Fund](https://prototypefund.de/), not a production-ready application.** The no-code desktop experience, general-purpose publication to multiple repositories, and one-click installation are goals under development. Current Engine, Workbench and validation capabilities are documented and testable; scientific approval and publisher acceptance are separate steps.
:::

**The promise:** less time wrestling with spreadsheets, scripts and metadata—and more time doing ecological research. FAIRmorph aims to guide researchers through **collecting, combining, cleaning, describing and checking data**, using accessible, domain-specific questions instead of requiring them to design every transformation themselves. The result should be research data that colleagues can **understand, trust and reuse**, with repeatable updates and support for established standards such as Darwin Core (DwC) and destinations such as PANGAEA. **The full guided, no-code experience remains a development goal.**

## Why FAIR data remains difficult

Existing standards do not automatically explain what a source column means or how to document, verify and publish it. A [2026 study on FAIR practices for ecologists](https://doi.org/10.1016/j.ecoinf.2026.103712) describes the gap between FAIR principles and actionable steps for researchers. In a [study of 100 archived ecology/evolution datasets](https://doi.org/10.1371/journal.pbio.1002295), **56% were incomplete** and **64% had limitations that partly or fully prevented reuse**. Those figures refer to that study's sample, not all published data.

**The challenge is the work between collecting data and making them genuinely reusable.** Researchers must bring together different sources, resolve inconsistent values, explain what fields mean, document methods and prepare metadata that another researcher can actually understand. FAIRmorph aims to guide this process through **ecology-specific, no-code interviews and reviewable steps**—while retaining the original data and making later updates repeatable. [Read the scientific background and limitations](/guide/overview/#research-evidence-the-fair-implementation-gap).

*Conceptual comparison:* FAIRmorph aims to reduce the effort of combining, cleaning and documenting ecological data, so results are easier to interpret, reuse and update. **Guided domain-specific interviews and complete no-code curation are planned capabilities**, not yet end-to-end features of the proof of concept.

**Good ecological research already takes care, knowledge and time. Preparing its data for others should not add an entirely new specialist project.** FAIRmorph's goal is to help with the whole journey: bring field observations together, tidy inconsistencies, explain scientific meanings through guided, domain-specific questions, check results and retain a clear record of every decision. This makes the data easier for **other researchers to find, understand and confidently reuse**—not just easier to export.

For researchers, that means less manual data wrangling and a more approachable, no-code path toward FAIR data. For data stewards, it means explicit definitions, inspectable review decisions and reproducible transformations. **Different formats and repositories are a useful outcome of well-curated data—not the only reason to curate them.**

## Better-prepared data. Less repeated work.

Ecological research rarely arrives as one tidy, self-explanatory table. Field records, species counts, locations, measurements and images may be collected at different times or by different people. Before another team can reuse them, somebody must bring them together, resolve ambiguities and document what the observations mean.

**FAIRmorph aims to make that work manageable through a guided desktop process.** Rather than hiding scientific choices inside an ad hoc script or spreadsheet, the researcher can document them explicitly, a data steward can review them, and future collaborators can follow how the cleaned dataset was produced. Those decisions can then be reused when observations change or another format is needed.

## One curation workflow, many outputs

**An illustrative research workflow:** Imagine a field team maintaining recurring wildlife surveys with observations, site information, counts, and photographs. A publication might require a Darwin Core Archive; a data repository might need a structured table and descriptive metadata; collaborators might need a GeoJSON overview.

<CardGrid>
  <Card title="1. Import and interpret" icon="document">
    Keep the source files unchanged. Explain what each field means, how units and missing values work, and which mappings are supported by the research methods.
  </Card>
  <Card title="2. Review and transform" icon="approve-check">
    Version the decisions, run a defined transformation, and retain checksums, output files, and a reproducible execution record.
  </Card>
  <Card title="3. Prepare target formats" icon="document">
    Use the **same curated data and provenance** as the basis for distinct output packages, with destination-specific schemas and metadata.
  </Card>
  <Card title="4. Update and repeat" icon="setting">
    On the next survey release, apply the reviewed configuration to the new source revision, verify the outputs, and document what changed.
  </Card>
</CardGrid>

**The benefit:** different representations of the same research observations can remain consistent, attributable, and easier to update. Publication, repository acceptance, and DOI assignment still require the relevant repository's own submission and review process.

## What works today?

**This proof of concept supports the application to Germany's Prototype Fund.** The purpose is to demonstrate that FAIRmorph's planned system is technically feasible, reproducible, and ready for further feature development—not to present a finished tool for research-data publication.

The prototype focuses on four concrete proof points:

1. **A real scientific end-to-end test case.** A pinned, publicly available CS-PHOC ecological dataset is imported unchanged, processed by the generic Engine and verified through an immutable technical RUN. Separate **dataset-specific validation code** generates DwC-A, PANGAEA-preparation TSV and GeoJSON **test outputs**, which are independently checked against the source. This demonstrates the data path, **not** generic publishing or scientific approval.
2. **Desktop build and bundled Engine sidecar.** The Workbench uses Svelte/Tauri with the Python Engine as a separate local application. Its release workflow is configured to build **Windows (NSIS)** and **Linux (deb/AppImage)** packages, bundle the Engine using PyInstaller, and smoke-test the sidecar. **The build pipeline is implemented; successful packaged release builds and easy installation on end-user machines are not yet demonstrated here.**
3. **Continuous integration and delivery structure.** Engine tests, Workbench Linux/Windows integration checks, the independent real-data validation CI, desktop packaging workflows, and automatic documentation deployment establish the intended repository and CI/CD structure. They provide a tested foundation for further features—not a guarantee that all future functionality or distributable packages already pass acceptance tests.
4. **The intended two-component architecture in working code.** A separate **Python Engine** owns imported sources, mappings, processing, immutable RUN evidence and verification; the **Tauri desktop Workbench** invokes it through a defined local process interface. Current UI workflows demonstrate project setup, import, technical pipeline execution and verification, while full scientific curation and publishing remain under development.

**What is not yet proven:** one-click installation, complete no-code scientific review, multi-repository publication for arbitrary ecological datasets, publisher acceptance or production reliability. Those are the next product and validation milestones.
