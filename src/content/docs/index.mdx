**The promise:** less time wrestling with spreadsheets, scripts and metadata—and more time doing ecological research. FAIRmorph aims to guide researchers through **collecting, combining, cleaning, describing and checking data**, using accessible, domain-specific questions instead of requiring them to design every transformation themselves. The result should be research data that colleagues can **understand, trust and reuse**, with repeatable updates and support for established standards such as Darwin Core (DwC) and destinations such as PANGAEA. **The full guided, no-code experience remains a development goal.**

**Built on open-source foundations, not a proprietary data stack.** FAIRmorph combines existing tools—Polars for processing and Svelte/Tauri for the desktop—with **reviewed scientific meanings, transparent decisions and verifiable RUN evidence**. Frictionless-based data descriptions and validation are planned; repository-specific exports remain separate. [See the FOSS architecture and evidence](/guide/prototype-fund/).

## Helping ecological data become FAIR and reusable

Ecological researchers already collect valuable observations and increasingly share them. Research on [putting FAIR into practice for ecologists](https://doi.org/10.1016/j.ecoinf.2026.103712) highlights the value of clear, actionable guidance. A [study of 100 archived ecology and evolution datasets](https://doi.org/10.1371/journal.pbio.1002295) found that **56% were incomplete** and **64% had limitations that partly or fully prevented reuse**. Those numbers describe that study's sample, not all datasets. They illustrate why **clear methods, understandable metadata and reusable preparation steps** matter alongside making files publicly available.

**The challenge is the work between collecting data and making them genuinely reusable.** Researchers must bring together different sources, resolve inconsistent values, explain what fields mean, document methods and prepare metadata that another researcher can actually understand. FAIRmorph aims to guide this process through **ecology-specific, no-code interviews and reviewable steps**—while retaining the original data and making later updates repeatable. [Read the scientific background and limitations](/guide/overview/#research-evidence-the-fair-implementation-gap).

## From scattered data work to guided, reusable curation

![Two workflows for ecological data curation: conventional work often involves Python or R scripts, manual configuration and field mapping, specialist data-curation knowledge, and repeated cleanup; FAIRmorph aims to combine original data, guided scientific review, versioned decisions and verifiable RUNs.](/img/curation-workflows.svg)

*Conceptual comparison:* Python/R scripts, manual configuration and expert field mapping are **common challenges, not universal requirements**. FAIRmorph already supports source preservation, selected technical transformations and verifiable RUNs; **guided no-code scientific review and general-purpose standards-based exports remain development goals**. See the [research evidence](/guide/overview/#research-evidence-the-fair-implementation-gap) and [implementation status](/guide/prototype-fund/).


**Good ecological research already takes care, knowledge and time. Preparing its data for others should not add an entirely new specialist project.** FAIRmorph's goal is to help with the whole journey: bring field observations together, tidy inconsistencies, explain scientific meanings through guided, domain-specific questions, check results and retain a clear record of every decision. This makes the data easier for **other researchers to find, understand and confidently reuse**—not just easier to export.

For researchers, that means less manual data wrangling and a more approachable, no-code path toward FAIR data. For data stewards, it means explicit definitions, inspectable review decisions and reproducible transformations. **Different formats and repositories are a useful outcome of well-curated data—not the only reason to curate them.**

### Every decision matters. Make it traceable.

FAIRmorph is designed to make ecological data preparation **transparent, versioned and reproducible**—so researchers and collaborators can understand not only the results, but **how those results were produced**.

The Engine already preserves original imported files, supports separately versioned **scientific field descriptions and mapping decisions**, and records explicit review actions. Completed processing **RUNs** retain pinned input and configuration snapshots, output manifests and integrity checks. This helps teams inspect which data and definitions were used, verify technical results and repeat documented processing steps when observations are updated.

For researchers, that means less dependence on forgotten spreadsheet edits. For data stewards and future users, it means clearer definitions, review history and processing evidence that can be examined independently. **The current audit is operation-specific:** it does not capture every individual cell change for every pipeline, and technically verified data are not automatically scientifically approved.

[How versioned field definitions, mapping decisions and RUN evidence work](/guide/overview/#transparent-versioned-and-reproducible-by-design).

**The aim is to support good ecological research—not replace researchers' expertise.** Researchers keep control of scientific meaning. Data stewards gain explicit definitions, inspectable decisions and reproducible processing. Future users gain better documented, more interpretable data.


## From field observations to reusable results

**An illustrative research workflow:** Imagine a field team maintaining recurring wildlife surveys with observations, site information, counts and photographs. FAIRmorph's intended guided workflow would help them bring these records together, explain what the fields mean, review quality checks and preserve a documented, repeatable path toward reuse. Different publication formats are one possible result—not the only goal.

  </Card>
  <Card title="3. Clean, check and document" icon="document">

**The benefit:** a clearer path from field observations to data that colleagues can understand, combine and build upon—with less repeated manual preparation. Publication, repository acceptance and DOI assignment still require their own scientific and institutional review.

## What works today?

**This proof of concept supports the application to Germany's Prototype Fund.** The purpose is to demonstrate that FAIRmorph's planned system is technically feasible, reproducible, and ready for further feature development—not to present a finished tool for research-data publication.

### Demonstrated / In development

| Area | **Demonstrated with technical evidence** | **In development or not yet demonstrated** |
| --- | --- | --- |
| **Engine** | Unchanged source imports, declarative tabular pipelines, versioned review contracts and verifiable RUN/2 evidence ([Engine tests](https://github.com/FAIRmorph/fairmorph-engine/actions)). | Broader end-to-end scientific publication integration and production-level reliability. |
| **Workbench** | Local project setup, source import, technical pipeline selection/execution and integrity checks ([Workbench CI](https://github.com/FAIRmorph/fairmorph-workbench/actions)). | Guided field-definition and mapping reviews, plus a complete no-code scientific workflow. |
| **Real-data validation** | Pinned CS-PHOC test: **16,940 recorded category cells** checked against the source; dataset-specific DwC-A, TSV and GeoJSON **test exports** independently audited ([validation results](/validations/docs/cs-phoc-reproduction-and-results/)). | Validation with additional independent datasets and formally reviewed scientific interpretations. |
| **Publication and delivery** | Engine Data Package and separate EML/DwC-A adapter tests; [v0.1.1](https://github.com/FAIRmorph/fairmorph-workbench/releases/tag/v0.1.1) built and automatically published Windows/Linux packages with a bundled Engine. Linux DEB/AppImage and portable Windows startup have been manually tested. | General-purpose Workbench export, fully verified graphical end-to-end workflows, publisher acceptance and production-scale reliability; [Windows console flash](https://github.com/FAIRmorph/fairmorph-workbench/issues/17) remains open. |

**Evidence vs. roadmap:** A passed technical test is not scientific approval or proof of a finished user-facing product. Read the [Prototype Fund evidence and six-month development plan](/guide/prototype-fund/) for test links, limitations and the proposed milestones.

The four technical proof points behind this summary are:

1. **A technical end-to-end validation on real research data.** A pinned, publicly available CS-PHOC ecological dataset is imported unchanged, processed by the generic Engine and verified through an immutable technical RUN. Separate **dataset-specific validation code** generates DwC-A, PANGAEA-preparation TSV and GeoJSON **test outputs**, which are independently checked against the source. This demonstrates the data path, **not** generic publishing or scientific approval.
2. **Desktop build and bundled Engine sidecar.** The Svelte/Tauri Workbench runs the Python Engine as a separate local application. The successful [v0.1.1 release run](https://github.com/FAIRmorph/fairmorph-workbench/actions/runs/43516992967) built, smoke-tested and automatically attached Windows (NSIS/ZIP) and Linux (DEB/AppImage) packages. Linux packages were manually launched or installed and the Windows portable app starts and reaches the Engine; a brief Windows terminal flash is a [known issue](https://github.com/FAIRmorph/fairmorph-workbench/issues/17).
3. **Tested integration and delivery.** Engine tests, Workbench Linux/Windows checks, independent real-data validation, a [successful multi-platform release and asset upload](https://github.com/FAIRmorph/fairmorph-workbench/actions/runs/43516992967), and automated documentation deployment demonstrate the CI/CD chain. They do not replace full manual desktop acceptance or future production-hardening tests.
4. **The intended two-component architecture in working code.** A separate **Python Engine** owns imported sources, mappings, processing, immutable RUN evidence and verification; the **Tauri desktop Workbench** invokes it through a defined local process interface. Current UI workflows demonstrate project setup, import, technical pipeline execution and verification, while full scientific curation and publishing remain under development.

**What is not yet proven:** complete guided scientific review, end-to-end graphical processing on every target platform, generic publication from the Workbench, publisher acceptance, or production reliability. Those are upcoming development and validation milestones.
